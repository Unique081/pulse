Module 1 documentation — endpoint, response format & use case

Endpoint used

GET https://api.openweathermap.org/data/2.5/weather?q={city}&units=metric&appid={API_KEY}

Response format

JSON — main.temp, main.humidity, weather[0].description, etc.

Use case

A trip-planning app could flag packing changes per city using this same call.

Module 2 documentation — data handling, display & privacy

How data is handled & displayed

Fetched JSON is held only in memory and mapped straight onto DOM elements via textContent — no reload, no storage of the response itself.

Privacy

Only the typed city name is sent. No tracking, no cookies, no persisted search history.

Module 3 documentation — automation, filtering & A/B testing

APIs used per category

  • Fashion — NewsAPI /v2/everything?q=fashion
  • Weather — OpenWeatherMap /data/2.5/weather
  • Entertainment — TMDb /3/trending/movie/day
  • Politics — NewsAPI /v2/everything?q=politics

NewsAPI localhost restriction — and its fix

NewsAPI's free tier blocks browser requests from anywhere but localhost, replying 426 corsNotAllowed instead of articles. newsApiFetch() detects that status and automatically retries through a CORS proxy that fetches server-side, so Fashion, Politics, and Trending work regardless of where the site is opened from.

Module 4 documentation — visualization, personalization & live dashboards

Dynamic input elements

  • Main search bar — types twice as hard: it filters whatever's already on screen as you type, and if you press Enter (or tap ↵) it runs a live API search scoped to whichever category is active — a city/town on Weather fetches and adds that city's card, a term on Politics/Fashion searches NewsAPI within that topic, a title on Entertainment searches TMDb. In every case the existing cards (the major cities, the regular feed) stay on screen — search results are added alongside them, never in place of them.
  • Weather — the filter bar's "add a city" box does the same city-add as the main search bar.
  • Entertainment — a genre <select>, populated from TMDb's live genre list, re-queries /discover/movie on change.
  • Fashion / Politics — a topic <select> narrows the NewsAPI query (e.g. politics → "elections").

Personalization

On load, navigator.geolocation requests the visitor's coordinates and fetches weather directly by lat/lon for the dashboard's "Local Weather" tile — falling back to a default city if permission is denied. A Preferences panel (⚙️) also lets a visitor set a default landing category, a home city, and a favorite movie genre, saved in localStorage and applied on every return visit.

Chart.js — mapping data to the right chart type

  • Line — the 5-day forecast, because the point is change over time.
  • Bar — movie ratings and city temperatures, because the point is comparing a number across named items.
  • Doughnut — article count by news source, because the point is share-of-whole.
  • Raw list — the top-5 headlines stay plain text; a ranked list of five items is already faster to scan than a chart would be. Not every number needs a chart.

Live dashboard mechanics

The Local Weather tile refetches every 10 minutes; the headlines tile updates whenever the trending banner refreshes (hourly, or via its ↻ button); the movies tile refreshes hourly alongside Entertainment. Each uses setInterval on its own schedule rather than one blanket page refresh, so a slow feed never blocks the others.

Display mode toggle (optional)

A "Both / Cards / Chart" switch above the feed lets a visitor collapse to whichever view suits the moment — the chart alone for a quick trend check, or cards alone to actually read. The setting applies instantly via applyViewMode() without a re-fetch.

Mobile-friendly practices

The category nav collapses behind a "☰ Categories" toggle under 640px; the dashboard and card grids drop from three/multi-column to a single column; charts use Chart.js's responsive mode inside a fixed-height wrapper so they resize with their container instead of overflowing it.

Module 5 documentation — personalization, reliability & performance

localStorage vs sessionStorage — used for different jobs

localStorage (survives closing the browser) holds anything that should follow the visitor back next time: preferences, bookmarks, the A/B variant, and the response cache. sessionStorage (cleared when the tab closes) holds only this-tab-right-now state — which category and view mode you're on — so a page refresh mid-visit resumes exactly where you were, but a fresh tab starts clean at your saved default.

Auto-filled forms

The Preferences form pre-fills every field from localStorage when opened. The main search box and the weather "add a city" box also pre-fill with your last search per category — convenient, but deliberately not auto-submitted, so returning to a tab never fires an API call you didn't ask for.

Bookmarks / saved locations

A ☆ button on every card saves it to localStorage under a stable id (city name, TMDb id, or article URL). The 🔖 panel lists everything saved, with one click to remove. Saved weather locations are folded back into the city-comparison list automatically on your next visit.

Loading states, errors & retry

Skeleton cards (pulsing placeholders) show immediately on every fetch instead of a blank grid. A failed request gets one silent automatic retry before anything is shown to the user; if that also fails, the grid shows a plain-language reason (offline, rate-limited, or blocked) plus a ↻ Retry button. A banner appears the moment the browser goes offline and clears itself when it's back.

Managing API rate limits

guardedFetch() keeps a rolling timestamp log per API (OpenWeatherMap, TMDb, NewsAPI) and refuses to send a request once a self-imposed ceiling is hit within its time window — the UI shows "rate limit reached, try again shortly" instead of risking a real 429 from the provider. Search and "add a city" buttons also briefly disable themselves after a click, so a double-tap can't fire the same request twice.

Avoiding redundant calls

Every category result is cached in localStorage for 5 minutes, keyed by category + filters (e.g. weather:Lagos,London,...). Switching Fashion → Weather → Fashion inside that window reloads instantly from cache with zero network calls; a small ↻ next to the category status forces a fresh fetch when you actually want one. Background refreshes (dashboard weather, movies, trending) also skip themselves entirely when document.visibilityState shows the tab isn't visible — a backgrounded tab burns no quota.

Debouncing & throttling

The on-screen filter (typing in the search box) is debounced 150ms so fast typing doesn't re-scan the DOM on every keystroke. Search and "add a city" actions are throttled with a 1-second cooldown per button.
